# SEVA MARKET INDIA — End-to-End Audit Report

Date of run: 2026-09-06 · App root: `seva-market-india/`

This report covers a full functional audit of the marketplace (pages, categories,
services, search + PIN, customer/provider flows, dashboard, buttons/forms, and
mobile behaviour). Every confirmed finding below was reproduced live, fixed in
code where it was a real defect, and re-verified on a fresh server run.
Tests are green: `npm test` **126/126** and `npm run check` **51/51** files.

## 1. Confirmed findings & fixes

### #1 — Logged-in homepage still showed "Log in" instead of Dashboard
A signed-in user hitting `/` was served the logged-out home (Log in / Sign up)
because the home route had no session-aware handling.
- **Fix:** `src/routes/pages.js` home handler now resolves the session and renders
  **Dashboard** for authenticated users and the marketing home for guests.
- **Verified:** with a live session cookie, `/` and `/categories` nav render
  `href="/dashboard">Dashboard` (no `Log in` link).

### #2 — State/location search didn't actually filter (and leaked across states)
`?state=…` was ignored (treated as free text), and a full-area query such as
`place=Guwahati` / `place=Assam` could not match a service pinned in a sub-district
(e.g. "Dispur, Guwahati, Kamrup Metropolitan, Assam"). In the worst case a whole-region
query would list services from other states.
- **Fix (subtree-aware search):** added `descendantIds(db, locationId)` to
  `src/models/location.js` — an indexed `search_text` LIKE-suffix walk that returns
  the node plus every row whose breadcrumb ends under it. `search-context.js` now
  parses `state` (by slug) first, falls back to `place` free text, resolves the
  matching area node, then passes `locationIds` (the subtree) into
  `searchServices` / `searchProviders` (`services.location_id IN (…)`).
- **Verified live:**
  - `?state=assam` → 4 services, all in Assam/Guwahati area (no cross-state leak).
  - `?state=maharashtra` → 3 services, all in Maharashtra.
  - `place=Kochi` → matches a service pinned at "682001, Kochi, Ernakulam, Kerala".
  - Full-area `place=Assam` → correctly **0** Maharashtra results (no leak).

### #3 — Stale "foundation build" copy on static pages
About / Contact / Privacy / Terms repeated a placeholder sentence claiming policies
would "ship with the provider onboarding milestone".
- **Fix:** full rewrite of the four static pages in `src/routes/pages.js` with
  concrete marketplace-accurate prose.
- **Verified:** grep for `foundation build` / `full policies ship` on `/about`,
  `/privacy`, `/terms` → **0** occurrences.

### #4 — Search results page had no way to refine the query
After searching, the results view offered no inline filter UI to change service /
location / PIN, forcing users back to the hero form.
- **Fix:** `/search` results page now renders a compact **refine bar** generated by
  `searchBarMarkup(filters, activeCat)` — service + city/state + PIN inputs plus a
  hidden `category` param that preserves any active category.
- **Verified:** the results page now carries the `action="/search"` form and its
  `q`/`pin`/`category` fields (2 matches on the form markers).

### #5 — Category & service catalogue were thin
- Out of 103 categories (10 parents + 93 leaves), **8 groups** had only a single
  leaf service, and only **14 seed services / 10 seed providers** were live in the
  DB — too sparse to demonstrate most category pages.
- **Code scope:** added live services for previously-thin groups and a third
  "makeup" category expansion (20/20/20 lists) per the approved scope. The
  remaining thinness (some category pages and search result counts still return
  few/no live listings) is **inherent content thinness** — it is a data-seeding
  matter, not a routing bug, and is flagged in §3 below rather than patched in code.

### #6 — Reviews and customer→provider flow
Public provider pages render services, contact strip (Call / view reviews), the
rating line, and a "Leave a review" form; the signed-in provider dashboard and
review POST round-trip were confirmed working earlier in the audit.
